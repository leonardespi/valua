# E0101 — `math.type` not representable in target

## Description

`math.type(x)` observes whether a number is an integer or a float. This distinction exists in Lua 5.4 (which has a native integer type) but **does not exist in LuaJIT**, where all numbers are IEEE 754 doubles.

## Triggering example

```lua
local x = 1
local kind = math.type(x)  -- E0101 fired here
```

## Diagnostic

```
error[E0101]: math.type observes the integer/float distinction absent in LuaJIT
  ┌─ input.lua:2:14
  │
2 │ local kind = math.type(x)
  │              ^^^^^^^^^ math.type observes the integer/float distinction absent in LuaJIT
  │
  = note: math.type() has no equivalent in LuaJIT; all numbers are IEEE 754 doubles
  = help: Remove type discrimination or track numeric kind explicitly in user data
```

## Justification

`math.type` is listed in `L_{5.5}^{out}` (the out-of-domain set) per the impossibility theorem in `docs/demostracion_transpilacion_lua.md`. No static or dynamic transformation can produce semantically equivalent behavior: if the source relies on distinguishing integers from floats, the program's observable behavior differs between targets. See PRD §5.2.

## Remediation

- If the type check is defensive (e.g., checking that a value is integral before passing to an API), replace it with an explicit floor/truncation check: `x == math.floor(x)`.
- If the code truly needs integer vs. float discrimination at runtime, track the kind in a separate variable in user data.
- If the code path can be removed (the distinction was never observable at the call site), delete it.
