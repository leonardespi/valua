# E0103 — `math.tointeger` not representable in target

## Description

`math.tointeger(x)` returns the integer representation of `x` if `x` is exactly representable as an integer, or `nil` otherwise. This function observes the integer/float distinction, which **does not exist in LuaJIT**.

## Triggering example

```lua
local x = 1.0
local n = math.tointeger(x)  -- E0103 fired here
return n
```

In Lua 5.4: `n == 1` (exact integer representation).  
In LuaJIT: `math.tointeger` does not exist; this would be a runtime error.

## Diagnostic

```
error[E0103]: math.tointeger observes the integer/float distinction absent in LuaJIT
  ┌─ input.lua:2:11
  │
2 │ local n = math.tointeger(x)
  │           ^^^^^^^^^^^^^^ math.tointeger observes the integer/float distinction absent in LuaJIT
  │
  = note: math.tointeger() has no equivalent in LuaJIT; all numbers are IEEE 754 doubles
  = help: Replace with math.floor() if truncation is intended, or restructure to avoid integer/float discrimination
```

## Justification

`math.tointeger` is part of `L_{5.5}^{out}` (out-of-domain set). Like `math.type`, it cannot be emulated in LuaJIT because the integer/float distinction it exposes does not exist. See PRD §5.2.

## Remediation

- If truncation toward zero is the intent, replace `math.tointeger(x)` with `math.floor(x)` (or `math.ceil`, depending on rounding direction). Note that `math.floor` does not return `nil` for non-integral values.
- If the `nil` sentinel (non-integral check) is essential to the logic, represent the check explicitly: `x == math.floor(x)`.
- If the call is dead code reachable only when `x` is always integral in practice, remove the check.
